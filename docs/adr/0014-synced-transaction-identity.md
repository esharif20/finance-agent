# A synced Transaction's identity is its provider transaction ID

SimpleFIN gives each Transaction an ID and each Account a current balance, but no running balance per Transaction, so ADR 0006's key cannot be built for synced rows. For Accounts synced through SimpleFIN only, this decision amends ADR 0006; CSV imports keep 0006's key unchanged. Each sync is one Statement Import holding the raw response.

**Identity.** A synced Transaction is identified by (Account, provider transaction ID). A posted row whose key already exists is recorded as also present in the new Statement Import and is never imported twice, so applying the same response twice changes nothing. Rows with different IDs are always distinct Transactions, even when every other field is equal. Two rows with the same ID in one response collapse to one if identical; if they differ, that Account's rows from that sync are rejected and the failure is logged as a count. A later row with a known ID but a different amount, date or description never changes the stored Transaction; the conflict is surfaced.

**Pending.** Only posted rows enter the Ledger. A pending row is kept in the raw response and nothing else: it creates no Transaction, takes part in no matching and counts in no total. When it posts, the posted row is handled as a new row whatever its ID, so a pending row that posts under a new ID, or is reverted, needs no special case.

**Reconciliation.** At each sync the provider reports `balance` B for each Account. At the first sync an anchor is fixed: A = B − (sum of the amounts of every Ledger Transaction in that Account). At every later sync k, the Reconciliation Gap is B_k − (A + sum of the amounts of every Ledger Transaction in that Account), in Decimal, in the Account's currency; a non-zero value opens a Reconciliation Gap linked to that sync's Statement Import. If the coverage spike shows that `balance` includes pending rows, the sum of the pending amounts in that response is subtracted from B first. A row missing from the feed therefore shows as a gap equal to its amount, and a double-counted one as a gap equal to its negation.

**Matching a synced row to a CSV row.** A synced Transaction and a CSV Transaction are candidates for the same purchase when all of these hold: same Account (the user links each synced Account to its CSV Account once, at connect), exactly equal amount and currency, equal normalised description (Unicode NFKC, casefolded, every character that is not a letter or digit removed), and Europe/London dates at most 3 calendar days apart. Each time a Statement Import is applied to an Account, take the Transactions in it that are not yet matched and build the graph whose edges are candidate pairs. Every connected component has a single amount and normalised description. In a component with k CSV and k synced Transactions, sort each side by date (CSV ties by file order, synced ties by provider ID) and pair them in that order; if every pair is within 3 days, each pair becomes one Transaction: the synced key is linked to the existing Transaction as also present in the sync's Statement Import, exactly as 0006 does for overlapping CSVs. Any other component (unequal counts, or a sorted pair more than 3 days apart) is ambiguous: every row stays its own Transaction, the component is surfaced as a Possible Duplicate, and it is re-evaluated each time a Statement Import is applied, so a later row that balances it resolves it automatically. A match is final once made. Pairing in sorted order is safe because all rows in a component have the same amount, so any valid pairing gives the same totals.

**Changed provider IDs.** A posted row with an unknown ID is a new Transaction, so if the provider re-issues an ID, the Transaction is counted twice and the sync opens a Reconciliation Gap. The new row and an existing synced Transaction are surfaced together as a Possible Duplicate when they have the same Account, amount and normalised description, dates at most 3 days apart, and the old ID is absent from a response whose date range covers the old Transaction's date. The user resolves it with a Correction (ADR 0001); nothing is ever deleted automatically.

Rejected: fuzzy auto-merging of ambiguous groups, because a wrong merge hides a real purchase, whereas a surfaced duplicate is visible both in the Possible Duplicate and in the Reconciliation Gap. The 3-day window and the normalisation are first guesses until the coverage spike reports real field formats; changing either needs a superseding ADR.
