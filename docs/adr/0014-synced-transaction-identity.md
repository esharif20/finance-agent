# A synced Transaction's identity is its provider transaction ID

SimpleFIN gives each Transaction an ID and each Account a balance, but no running balance per Transaction, so ADR 0006's key cannot be built for synced rows. For Accounts synced through SimpleFIN only, this decision amends ADR 0006; CSV imports keep 0006's key (and any amendment from #34) unchanged. Each sync is one Statement Import holding the raw response.

**Identity.** A synced Transaction is identified by (Account, provider transaction ID). Provider Account and Transaction IDs are opaque strings: compared byte for byte, never parsed, trimmed or treated as numbers. Identity and matching use only raw source fields as received (amount, currency, raw description, date); never Merchant, Category, Kind or anything else derived, so changing a normaliser, rule or taxonomy never changes identity. A posted row whose key already exists is recorded as also present in the new Statement Import and is never imported twice, so applying the same response twice changes nothing. A later row with a known ID but a different amount, date or description never changes the stored Transaction; it is listed in the sync report. Two rows with the same ID in one response collapse to one if identical; if they differ, that Account's rows from that sync are rejected and the failure is logged as a count. Rows with different IDs are always distinct Transactions, even when every other field is equal: providers have sent one purchase several times under different IDs, but the rows may be real, so they are kept and surfaced (see Possible Duplicates), never merged.

**Dates.** A synced row's date is its `posted` timestamp as a Europe/London calendar date; `transacted_at` is stored but used for nothing here. A CSV row's date is the date in the file.

**Pending.** Only posted rows enter the Ledger. A pending row is kept in the raw response and nothing else: it creates no Transaction, takes part in no matching and counts in no total. When it posts, the posted row is handled as a new row whatever its ID, so a pending row that posts under a new ID, or is reverted, needs no special case.

**Reconciliation.** Each response reports, per Account, `balance` B at instant `balance-date` t. The coverage spike (#26) found `balance` equal to `available-balance` even with a pending row present, so `balance` includes pending rows: B is first reduced by the sum of that Account's pending amounts in the same response, both for the anchor and at every later sync; otherwise every pending card payment would open a spurious Gap. The first sync fixes the anchor (B₁, t₁). At every later sync k, the Reconciliation Gap is B_k − B₁ − (sum of the amounts of the Account's Ledger Transactions whose instant is in (t₁, t_k]), in Decimal, in the Account's currency. A Transaction's instant is its synced `posted` timestamp, or, for a CSV Transaction with no synced match, the end of its date in Europe/London. A non-zero value opens a Reconciliation Gap linked to that sync's Statement Import. CSV history before t₁ never affects it; a row missing from the feed shows as a Gap equal to its amount, a double-counted one as a Gap equal to its negation.

**Matching a synced row to a CSV row.** The user links each synced Account to its CSV Account once: at `fa connect`, or with `fa connect --link` for a CSV Account first imported after connecting. Until linked they stay two Accounts, never merged by guesswork, and `fa import` says so. A CSV Transaction and a synced Transaction in that Account are a candidate pair when: amount and currency are exactly equal; normalised descriptions are equal and non-empty (raw description, Unicode NFKC, casefolded, every character outside Unicode categories L and N removed); and dates are at most 3 calendar days apart. After any Statement Import (CSV or sync) is applied to the Account, take every Transaction in the Account not yet matched, from either source, and build the bipartite graph whose edges are candidate pairs. In each connected component (one amount and one normalised description, by construction), sort the CSV side by (date, order recorded) and the synced side by (date, provider ID). If both sides have k rows and every i-th pair is at most 3 days apart, each pair becomes one Transaction: the CSV Transaction stays, and the synced key is linked to it as also present in the sync's Statement Import, exactly as 0006 does for overlapping CSVs; later syncs find it by that key, and its instant is the synced `posted` timestamp. Any other component is ambiguous: every row stays its own Transaction and the component is a Possible Duplicate, re-evaluated after the next Statement Import, so a later row that balances it resolves it automatically. Matching never pairs two CSV or two synced Transactions and pairs each Transaction at most once, so 0006's counts are kept. A match is final once made. Pairing in sorted order is safe only when the count of pairs is determined: all rows in a component have the same amount, so any two valid pairings of the same size give the same totals. Which components resolve is amended below (#74).

**Possible Duplicates** are also surfaced, never merged, for a synced Transaction with an unknown ID when another synced Transaction in the Account has the same amount and raw description and either (a) the same date in the same response, or (b) a date at most 3 days away and an ID absent from a later response whose date range covers it (a re-issued ID; the sync also opens a Reconciliation Gap). The user resolves any Possible Duplicate with a Correction (ADR 0001); nothing is deleted automatically.

Rejected: fuzzy auto-merging of ambiguous groups, because a wrong merge hides a real purchase, whereas a surfaced duplicate is visible both as a Possible Duplicate and in the Reconciliation Gap. The 3-day window and the normalisation are first guesses until the coverage spike reports real field formats; changing either needs a superseding ADR. `tests/test_adr_0014_matching.py` is the executable statement of the matching rule.

## Amendment (#74): matching knows each source's coverage

The rule above resolves a component whenever some pairing uses every row. That loses a purchase when the component also has a smaller pairing. Take coffees on 1, 3 and 5 Jan, with the CSV holding 1–3 Jan and the sync 3–5 Jan. Sorted pairing gives (1, 3) and (3, 5), so three purchases become two. No Possible Duplicate is surfaced, and no Gap opens because the lost row is CSV history before the anchor. Rows alone can't tell this from two purchases posted 2 days late, so matching now uses where each source is complete.

**Coverage.** Per Account and per source, the complete days are the union, over that source's Statement Imports, of the days each one holds in full. A CSV export is a contiguous window of the Bank's history (ADR 0006), but it may cut its first and last days, so it holds the days strictly between its first and last row's dates. A sync asks from London midnight, so it holds the days from its first row's posted date up to the day before its last row's. Both are taken from the rows stored for that Statement Import, so no schema change is needed. Narrower coverage is always safe: it can only make more components ambiguous, never merge more.

**Which components resolve.** A row is *required* when every date its counterpart could have (its date ± 3 days) is a complete day of the other source, so the other source must hold that counterpart. Any other row is *optional*: its counterpart may lie outside the other source. Each matching (candidate pairs, one-to-one) that pairs every required row is a consistent explanation. The component resolves only if at least one explanation exists and they all have the same size. Then it merges a maximum one, in date order when every row is paired, as before. Otherwise it is ambiguous: every row stays its own Transaction and the component is a Possible Duplicate, re-evaluated after every Statement Import, so it resolves once coverage grows. When both sources are complete around every row, this is exactly the old rule.

This holds two guarantees. A purchase that a complete source lists is never merged away, and an unmerged double is always inside a surfaced Possible Duplicate. The cost is that rows within 3 days of an edge both sources share stay surfaced until a later Statement Import covers past that edge. That happens, for example, when a CSV and a sync end on the same day. The code checks the rule in polynomial time: it builds a maximum matching that pairs every required row (Mendelsohn–Dulmage), then looks for an alternating path that starts at an optional CSV row and ends at an optional synced row, both through paired edges. Such a path is exactly a smaller explanation. `tests/test_adr_0014_matching.py` states the rule by brute force over all matchings and checks the code against it.

Rejected: the issue's first proposal, which paired only rows inside both coverages and surfaced every row in the 3-day band. It surfaces boundary rows even where the other source must hold their counterpart, such as a CSV row near the sync's start, inside a CSV that covers the sync. Choosing the explanation with the least date skew was rejected too: it is a guess, and a wrong guess hides a purchase.

Shortcut: a sync's coverage ends at its last posted row, not its `balance-date`, because only the rows are stored per Statement Import. Storing each sync's requested start and `balance-date` would extend coverage to the fetch time and resolve edge bands sooner. Upgrade if edge bands stay surfaced too long in real use.
